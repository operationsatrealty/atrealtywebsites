# Tom McCartney — Ray White Manurewa

Marketing site for **tommccartney.co.nz**. Static HTML/CSS/JS, generated by a small
build step that pulls Tom's live listings and settled sales from VaultRE.

```bash
npm install
npm run build          # → dist/   (needs VaultRE credentials, see below)
npm run build:offline  # → dist/   (skips VaultRE, uses data/listings.json)
npm run preview:file   # → dist-preview/index.html, one self-contained file
```

---

## Where the numbers come from

Everything on the page — the three current listings, the sold table, and every
figure in the stat rows — is Tom's real data from **VaultRE**, A T Realty's CRM.
Nothing is hand-typed, so nothing goes stale by being forgotten.

`vaultre.mjs` is a trimmed port of `atrealty-next/src/lib/vaultre.ts` — same base
URL, endpoints, auth and field mapping, so this site and the main Next.js site can
never disagree about an agent's numbers.

**Tom has staff records in two offices** (Manukau *and* Manurewa), each with its own
listings attached. Both are fetched and merged. Checking only one would silently
drop part of his history.

### Credentials

Set in the Vercel project's **Environment Variables** (Production + Preview), and in
a local `.env.local` for development:

| Variable | Notes |
|---|---|
| `VAULTRE_API_KEY` | One value, shared across the whole group |
| `VAULTRE_BEARER_TOKEN_MANUKAU` | Per office — each office is its own VaultRE account |
| `VAULTRE_BEARER_TOKEN_AUCKLAND_CENTRAL` | |
| `VAULTRE_BEARER_TOKEN_MANUREWA` | |
| `VAULTRE_BEARER_TOKEN_MANGERE_BRIDGE` | |

Tom only needs the shared key plus **Manukau** and **Manurewa**. The same values are
already in `atrealty-next/.env.local`.

Locally: `node --env-file=../../atrealty-next/.env.local build.mjs`

### Why build-time and not a browser fetch

This is a static site. Fetching VaultRE from the browser would mean shipping the API
key and bearer token in readable JavaScript, where anyone could take them. The build
runs on the server, bakes the results into the HTML, and ships no credentials at all.
It also means the property content is in the HTML for Google to index, which a
client-side fetch would not achieve.

**Never move these calls client-side.**

### Keeping it fresh

The trade-off is that data is only as current as the last deploy. Set a **Vercel Cron
Job** (or a scheduled GitHub Action) to trigger a redeploy — daily is plenty for an
agent site. Without one, the listings freeze at the last push.

### If VaultRE is down

The build does **not** fail. It falls back to `data/listings.json` — the last good
snapshot, refreshed automatically on every successful build — and logs that it did
so. A CRM outage must never be able to take the website down.

## Images

VaultRE serves property photos at full print resolution: 4500×3000, 3.5–4.6 MB each.
Its CDN ignores every resize parameter, so linking straight to it would put roughly
12 MB of images on the page.

`build.mjs` downloads, resizes and re-encodes them with `sharp` into
`dist/assets/listings/`, content-hashed for immutable caching. **15 MB of source
images become about 390 KB**; the whole site is under 500 KB.

Downloads are cached in `.image-cache/` (gitignored), so repeat builds don't refetch.

### The portrait is the weak link

The only headshot in the Supabase `agent-photos` bucket is **1280×720 — landscape**.
Every upright frame on the page is therefore a heavy crop of it, done with sharp's
`attention` strategy so it centres on Tom rather than the middle of the frame. The
largest square it can yield is 720×720, which is the ceiling on sharpness here.

**Uploading a higher-resolution portrait to that bucket would improve the site with
no code change.** Tom has 6000×4000 photos available.

## The appraisal form

The contact section embeds a form from the A T Realty marketing-forms app:

```html
<script src="https://atrealtygroup.co.nz/mkt-forms-embed.js" async></script>
<div data-atr-form="sales-appraisal-renuka-bisht-2"></div>
```

The slug reads wrong but **is correct**. That form is named *"Sales Appraisal - Tom
McCartney"* and its assignee is `tom.mccartney@raywhite.com`. It was created by
duplicating Renuka Bisht's form and the duplicate kept her slug. Renaming the slug in
the admin would break this embed unless `FORM_SLUG` in `build.mjs` is updated to match.

> **Open item:** the form has no notification row, so a submission is stored but
> **nobody is emailed**. Add an email notification in the marketing-forms admin
> before launch, or leads will sit unseen in the dashboard.

In `--preview` builds the embed is replaced with a placeholder, because the preview
is meant to be shareable in contexts that block third-party scripts.

## Design notes

Ray White brand colours and fonts are unchanged from *Brand in brief* — yellow
`#FFE512`, Lato, Playfair Display. What changed in the 2026-08 revision is restraint:
yellow is now an accent (one CTA, the eyebrow rules, the nav underline) rather than a
fill, the emoji section icons and the decorative `01–06` numbering are gone, the
animated counters are gone, and drop shadows are replaced with hairline rules. The
single dark band on the track record is the one deliberate moment of contrast.

The page is intentionally light-only. Every colour is painted explicitly rather than
inherited, so it holds up wherever it's embedded.
